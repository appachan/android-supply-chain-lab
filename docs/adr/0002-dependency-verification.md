# 2. Dependency verification with Dependabot

Date: 2026-10-31

## Status

Accepted

## Context

Gradle の依存検証（`gradle/verification-metadata.xml`）は、ビルドが使うプラグインとライブラリを検証する。ADR-0001 の wrapper の検証が守らない範囲である。

一方で、Dependabot は metadata を更新しない。版を上げた PR は未知の成果物で必ず失敗する。[Gradle のドキュメント](https://docs.gradle.org/current/userguide/dependency_verification.html)は、生成はリポジトリにあるものを信頼するだけなので人が確認するように求めている。PR を通すために無条件に再生成すると、検証の意味がなくなる。

## Decision

- 検証はチェックサムと PGP 署名を併用する（`--write-verification-metadata pgp,sha256`、`verify-signatures` は `true`）
- keyring は armored の `gradle/verification-keyring.keys` を commit する
- `verify` は鍵サーバーを使わない（`<key-servers enabled="false">`）。再生成では到達できる 2 台から鍵を取得する
- `*-sources.jar` と `*-javadoc.jar` は `trusted-artifacts` で検証の対象から外す
- Dependabot の Gradle の PR では、依存のコードを実行する読み取り専用のジョブと、書き込むジョブを分ける
  - `Regenerate verification metadata`（`pull_request`、`contents: read`）が metadata と `gradle.lockfile`（ADR-0003）を再生成して artifact にする
  - `Commit verification metadata`（`workflow_run`、`main` の定義）は PR のコードを実行せず、artifact をデータとして検査し、API でコミットする
- Gradle の `cooldown` は `default-days: 7` で、`androidx.*` を対象外にする（「cooldown と Google Maven のライブラリ」）
- 検査では、再生成では起こらない変更（検証設定の変更、既存の値の変更、信頼する鍵の署名の検証失敗）を機械的に拒否する。残りの差分をコミット本文に分類して出し、人が確認する
- CI の成功は metadata の承認として扱わない。人が差分を確認して merge する。auto-merge は使わない

## 論点ごとの結論

### 1. 生成の方式

`pgp,sha256` を採用する。公式は両方の併用を勧めていて、SHA-1 と MD5 は安全でないとしている。SHA-256 と SHA-512 の優劣は書かれていないので、Gradle の例で標準の SHA-256 を使う。

署名の利点は運用の負荷にある。信頼する鍵で署名された成果物は metadata にハッシュを持たないので、版が上がっても差分が出ない。今回の AGP 9.3.3 から 9.5.0 への更新で、metadata の増加は 11 行だった。人が確認する対象が、新しい鍵と無署名の成果物に絞られる。

Google Maven の成果物に署名がないという前提は、現在は正しくない。[Jetpack は 2023 年 6 月から署名されていて](https://developer.android.com/jetpack/getting-started)、公式ページが信頼する鍵を 4 件公開している。生成した metadata の `androidx` の鍵はこの 4 件と一致した。`com.android.tools.build:aapt2` も全 OS の jar に `.asc` があった。

生成の結果（`main` の metadata）は次のとおり。

| 項目 | 件数 |
| --- | --- |
| 信頼する鍵（`trusted-key`） | 56 |
| ハッシュまたは個別の鍵で検証する component | 41 |
| 無署名の成果物の行（`Artifact is not signed`） | 50 |

無署名として残るのは、署名の開始より前の `androidx` の版（`androidx.arch.core` など）、`com.google.testing.platform`、`bundletool`、`jetifier` などである。

keyring は armored にする。バイナリの `.gpg` は diff を読めず、両方あるとバイナリが優先される。ファイルの先頭の `pub` と `uid` の行で持ち主を読めるが、認証された情報ではない。信頼の根拠は `verification-metadata.xml` の fingerprint であり、keyring ではない。

### 2. 網羅性

OS ごとの成果物: `aapt2` は署名で検証されるので、metadata に OS ごとのハッシュは 1 件もない。Linux の CI で再生成した PR #3 の metadata を使い、macOS の空の `GRADLE_USER_HOME` で dependency verification の strict モードでビルドして成功した。`aapt2-9.5.0-16666295-osx.jar` が取得され、metadata の `aapt2` への言及は 0 件である。

条件は、OS ごとの成果物が信頼する鍵で署名されていることである。無署名の OS 別成果物が増えると Linux の再生成では記録されず、macOS のビルドが失敗する。失敗する側に倒れるので、そのときは手元で再生成して足す。

sources と javadoc: 全成果物の sources と javadoc の取得を `ArtifactResolutionQuery` で再現したところ、ルールがないと 16 件が失敗し、`trusted-artifacts` を足すと成功した。Android Studio そのものでは確認していない。公式が注意するとおり、これらは改ざんされても検知しない。実行されるコードではないので許容する。

plugin と buildscript: 検証の対象に含まれる。PR #1 の最初の失敗も buildscript の `classpath` で起きた。

再生成は同じコマンドで 2 回実行する。原因と根拠は「2 回の再生成が必要な原因」に書く。

手元で再生成するときは、空の `GRADLE_USER_HOME` を使う。strict モードのビルドに使った環境で再生成すると、不要な行が 19 行追加された。macOS と Linux で同じ 19 行だったので、OS の差ではない。

最初の生成は鍵サーバーの影響を受ける。1 回目は 17 件の鍵が取得できず `ignored-key` になった。同じ鍵を curl で取得すると成功するので一時的な失敗である。keyring に鍵が揃った状態で `ignored-keys`、`trusted-keys`、`components` を消して生成し直すと、ignored key は 0 件になり、2 回の生成の差分もなくなった。Linux の CI で同じ入力から再生成しても差分は出なかった（[run 41073618308](https://github.com/appachan/android-supply-chain-lab/actions/runs/41073618308)）。

### 3. Dependabot との両立

Dependabot は metadata を更新しない。公式の [Gradle の節](https://docs.github.com/en/code-security/dependabot/ecosystems-supported-by-dependabot/supported-ecosystems-and-repositories)に記述がなく、[dependabot-core の issue #1996](https://github.com/dependabot/dependabot-core/issues/1996) は未解決である。実際に [PR #1](https://github.com/appachan/android-supply-chain-lab/pull/1) の変更は `gradle/libs.versions.toml` だけで、CI は検証で失敗した（[run 41076405899](https://github.com/appachan/android-supply-chain-lab/actions/runs/41076405899)）。

無条件の再生成は改ざんを通す。偽の Maven リポジトリから改ざんした成果物を配信して再生成すると、exit 0 で成功し、次の行が書かれた。

```xml
<also-trust value="5dbcedca17d860c062cf3b0c894c14c2c2d576bba77f38a8795519e8705be738"/>
```

```xml
<ignored-key id="FF6E2C001948C5F2F38B0CC385911F425EC61B51" reason="PGP verification failed"/>
<sha256 value="7fe357..." origin="Generated by Gradle" reason="PGP signature verification failed!"/>
```

そこで `.github/scripts/review_verification_metadata.py` が、現在の PR の metadata と再生成の結果を比較する。

拒否するもの（コミットしない）:

- `verify-metadata`、`verify-signatures`、`keyring-format`、`key-servers`、`trusted-artifacts` の変更
- 既存のハッシュの削除、変更、`also-trust` の追加
- `PGP verification failed` で無視された鍵

人が確認するもの（コミット本文に出す）:

| 項目 | 確認すること |
| --- | --- |
| 信頼する鍵の追加と範囲の拡大 | fingerprint を配布元の公式情報と照合する。`^com[.]google...` のような regex の範囲が妥当か確認する |
| ignored key の追加 | 鍵サーバーの一時的な失敗か、未知の鍵か確認する |
| ハッシュで受け入れる成果物 | 初回の信頼である。`[group has trusted keys: check for a dropped signature]` が付いた行は、前の版の署名の有無を確認する |

metadata に出ない判断も人が行う。Dependabot は互換性の表を見ないので、PR #3 の AGP 9.5.0 と Gradle 9.8.2 は Kotlin 2.4.21 の Fully supported の範囲を超えているが、CI は成功する。範囲内に留めるなら `@dependabot ignore` か `ignore` の設定で除外する。この lab では提案を見るために `ignore` を設定していない。

Gradle の更新は `groups` で 1 つの PR にする。全ての PR が同じ metadata を変更するので、分けると 1 つの merge で残りがコンフリクトする。

`[dependabot skip]` を再生成コミットに付ける。[公式](https://docs.github.com/en/code-security/dependabot/working-with-dependabot/managing-pull-requests-for-dependency-updates)によれば、Dependabot は追加コミットのある PR の rebase を止めるが、この文字列があれば force-push で上書きする。PR #3 では、`main` との間にコンフリクトを作って Dependabot のジョブを起動すると、再生成コミットを捨てて PR を作り直し、その `synchronize` で再生成が自動で再開した。Dependabot がコミットを捨てても、信頼の判断は次の再生成コミットで同じように確認できる。

コンフリクトを作っただけでは Dependabot のジョブは起動しなかった。15 分待っても run がなく、`dependabot.yml` の変更で起動した。実際の運用では、次の定期実行か `@dependabot rebase` まで待つ可能性がある。PR #1 は同じジョブの後も `CONFLICTING` のままだったが、`[dependabot skip]` なしのコミットがあることに加えて、グループ化で個別の更新の対象外になっているので、原因は切り分けられていない。

cooldown は 7 日に設定するが、Google Maven のプラグインには効かない。公開から 2 日の AGP 9.5.0 が提案された。ログは `Using POM Last-Modified fallback release dates for com.android.application from https://plugins.gradle.org/m2` と `Filtered out 0 version(s) due to cooldown` を出している。Plugin Portal は Maven Central へ 303 でリダイレクトし、Central は 404 を返すが、その応答に `Last-Modified: Sat, 11 Oct 2025` が付いている。[dependabot-core の実装](https://github.com/dependabot/dependabot-core/blob/fdbe8b342118a62ac97da47e824666df11046fec/gradle/lib/dependabot/gradle/package/version_release_date_fallback_fetcher.rb)は status を確認せずにこの値を公開日として使う。ライブラリの除外は公開日に関係しない。結果と対処は「cooldown と Google Maven のライブラリ」に書く。

比較した案:

| 案 | 判定 | 理由 |
| --- | --- | --- |
| 人が手元で再生成して push | 不採用 | 全ての PR に手作業が必要。検証なしで新しいプラグインを開発者の環境で実行する |
| `pull_request` の 1 ジョブで再生成と push | 不採用 | 検証なしで実行する依存のコードと書き込み token が同じジョブに入る |
| `pull_request_target` で PR を checkout | 不採用 | 下記のとおり、書き込み token と Actions シークレットで PR のコードを実行する |
| PAT か GitHub App でコミット | 保留 | CI は通常どおり起動するが、シークレットが増える。署名の扱いも変わる |
| Dependabot の PR だけ検証を切る | 不採用 | 検証が必要な変更で検証を止める |
| 読み取りの再生成と `workflow_run` のコミットの分離 | 採用 | 書き込み token のあるジョブでは PR のコードが動かない |

### 4. CI の安全性

Dependabot の PR で実測した token は次のとおり。`permissions: contents: write` を宣言した probe の `GITHUB_TOKEN Permissions` のログによる。

| イベント | Contents | Secret source | Cache mode | 実行 |
| --- | --- | --- | --- | --- |
| `pull_request` | write | Dependabot | write | [run 41076405802](https://github.com/appachan/android-supply-chain-lab/actions/runs/41076405802) |
| `pull_request_target` | write | Actions | read | [run 41076402192](https://github.com/appachan/android-supply-chain-lab/actions/runs/41076402192) |

[公式](https://docs.github.com/en/code-security/dependabot/troubleshooting-dependabot/troubleshooting-dependabot-on-github-actions)の読み取り専用の扱いは既定値で、`permissions` を宣言すれば昇格する。Dependabot の PR は安全という前提は成り立たない。`pull_request_target` は Actions シークレットまで使えるので、PR のコードを checkout して実行すると、[公式の警告](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)のとおり危険である。Gradle は依存のプラグインをビルド中に実行するので、再生成そのものが信頼できないコードの実行である。

`Regenerate` は `contents: read` で `persist-credentials: false` にする。Dependabot のシークレットは使わない。`gradlew` の前に wrapper validation を実行する。PR は merge コミットではなく head を checkout する。

`Commit` の `if` で、`pull_request` からの実行、同じリポジトリ、`dependabot/gradle/` で始まるブランチを確認する。`workflow_run` は fork の PR でも書き込み token で動くので、`head_repository` の確認が境界になる。`Regenerate` の `if` は PR 側の定義なので、ここには頼らない。ブランチ名は env を経由して渡す。`github.actor` は判定に使わない。[Dependabot を使う confused deputy の攻撃](https://boostsecurity.io/blog/weaponizing-dependabot-pwn-request-at-its-finest)があるからである。

artifact は信頼しない。`Regenerate` が侵害されていれば内容は任意になる。`Commit verification metadata` は決まった 2 ファイルと PR の tree にある `gradle.lockfile` だけを読み、実行しない。検査のスクリプトは `main` の定義である。ただし、検査は構文上の検査で、正しさの証明ではない。新しい成果物に悪意のあるハッシュを書かれても区別できないので、人の確認が残る。

`GITHUB_TOKEN` の push では CI が通常どおり動かない。[公式](https://docs.github.com/en/actions/concepts/security/github_token)のとおり、`pull_request` の run は `action_required` で作られ、書き込み権限を持つ人が Approve workflows to run で開始する。実際に PR #1、PR #3 とも `action_required` になった。そこで `Commit` が `workflow_dispatch` で CI を実行する。この例外は同じページに書かれている。`verify` の check run は app 15368（GitHub Actions）で head の SHA に作られ、`pull_requests` に PR #3 が入った（[run 41082196141](https://github.com/appachan/android-supply-chain-lab/actions/runs/41082196141)）。

署名付きコミットは `createCommitOnBranch` で作る。`GITHUB_TOKEN` で作ったコミットは author が `github-actions[bot]`、committer が GitHub で、`verification.verified` は `true`、reason は `valid` だった（[commit 625d53c](https://github.com/appachan/android-supply-chain-lab/commit/625d53c1)）。`expectedHeadOid` で、再生成の間に更新されたブランチへの書き込みを防ぐ。

### 5. 失敗の確認

CI の結果:

| 条件 | 結果 | 実行 |
| --- | --- | --- |
| metadata のハッシュを 1 文字変更（`startup-runtime-1.1.1.aar`） | 失敗 | [run 41076427124](https://github.com/appachan/android-supply-chain-lab/actions/runs/41076427124) |
| 未知の無署名の依存を追加（okio 3.0.0） | 失敗 | [run 41076435292](https://github.com/appachan/android-supply-chain-lab/actions/runs/41076435292) |
| Dependabot の更新で metadata がない | 失敗 | [run 41076405899](https://github.com/appachan/android-supply-chain-lab/actions/runs/41076405899) |

手元の結果（macOS、偽の Maven リポジトリを最優先にして配信）:

| 条件 | 検証の方式 | 結果 |
| --- | --- | --- |
| 改ざんなし（対照） | | 成功 |
| `junit-4.13.2.jar` に 1 byte 追加 | 署名 | 失敗 |
| `startup-runtime-1.1.1.aar` に 1 byte 追加 | ハッシュ | 失敗 |
| `junit-4.13.2.jar.asc` を削除 | 署名 | 失敗 |
| Gradle キャッシュ内の `junit-4.13.2.jar` に 1 byte 追加 | 署名 | 失敗 |
| 上記のあと更新時刻を過去に戻す | 署名 | 失敗 |

ADR-0001 の配布物と違い、キャッシュ済みの依存も改ざんを検知した。

```text
> Dependency verification failed for configuration ':app:debugRuntimeClasspath'
  One artifact failed verification: startup-runtime-1.1.1.aar (androidx.startup:startup-runtime:1.1.1) from repository maven
  This can indicate that a dependency has been compromised. Please carefully verify the checksums.
```

未知の依存の確認では、同時に追加した `commons-text` は失敗しなかった。`org.apache.commons` のグループを信頼する鍵で署名されているからである。グループ単位の信頼は、そのグループの新しい成果物を自動で受け入れる。

## 2 回の再生成が必要な原因

PR #1 では 1 回の再生成で `bc-jdk18on-bom-1.80.2.pom` の行が書かれず、再生成した commit の strict モードのビルドが失敗した（[run 41076964846](https://github.com/appachan/android-supply-chain-lab/actions/runs/41076964846)）。

### 確認できた事実

Gradle 9.7.1 の[ソース](https://github.com/gradle/gradle/tree/v9.7.1/platforms/software/dependency-management/src/main/java/org/gradle/api/internal/artifacts)から:

- 親 POM と import した BOM は `ExternalResourceResolverDescriptorParseContext` で解決され、子の `sources` に追加される。`DependencyVerifyingModuleComponentRepository` は `sources` の各 POM について、子を解決したリポジトリの名前で `onArtifact` を呼ぶ
- `.asc` はそのラッパーのリポジトリから取得する。コンテンツフィルターの対象外の group でも取得を試みる（下記のログ）
- strict モードの `ChecksumAndSignatureVerificationOverride` は `(artifact, repositoryId)` で重複を除くので、同じ POM をリポジトリごとに検証する
- writer の `WriteDependencyVerificationFile` は `LinkedHashSet` に `(id, kind, file)` で登録するので、リポジトリによらず最初の 1 件だけが残る

lab の実物での観察:

- Google Maven の `sdk-common-32.5.0.pom` が `bc-jdk18on-bom:1.80.2` を `dependencyManagement` で import している。この BOM は Maven Central にしかなく、`.pom.asc` と `.module` がある
- 空の環境の strict モードのビルドのログ。Central から `.pom.asc` を取得したうえで、同じ POM の `.asc` を Google にも探して 404 になり、Google 経由の検証で失敗している

```text
Downloading https://repo.maven.apache.org/maven2/org/bouncycastle/bc-jdk18on-bom/1.80.2/bc-jdk18on-bom-1.80.2.pom.asc
Resource missing. [HTTP GET: https://dl.google.com/dl/android/maven2/org/bouncycastle/bc-jdk18on-bom/1.80.2/bc-jdk18on-bom-1.80.2.pom.asc]
One artifact failed verification: bc-jdk18on-bom-1.80.2.pom (org.bouncycastle:bc-jdk18on-bom:1.80.2) from repository Google
```

- `.asc` を探す先が 404 だったもののうち、Google のフィルターの対象外の group はこの 1 件だけだった
- 再生成の 2 回目に書かれる行は `reason="Artifact is not signed"` だが、この POM は Central で署名されている。この記録は Google 経由の探索の結果であり、コミット本文の `[group has trusted keys: check for a dropped signature]` はこの場合は誤検知である
- `--write-verification-metadata sha256` だけなら、空の環境の 1 回目で POM の行が書かれる。欠けるのは `pgp` を指定したときで、POM を見落としているのではない。ただし `verify-signatures` が `true` のままでは代わりにならない。この実行は 2246 行増え、未信頼の鍵で署名された groovy の 4 件で strict モードのビルドが失敗した

実験の結果。AGP 9.5.0 への更新を、それぞれ空の `GRADLE_USER_HOME` で実行し、別の空の環境の strict モードのビルドで判定した。

| 手順 | 追加行 | strict モードのビルド |
| --- | --- | --- |
| 再生成 1 回 | 6 | 失敗 |
| `--refresh-dependencies` 付きで 1 回（2 回試行、結果は同一） | 6 | 失敗 |
| 再生成 2 回、`--rerun-tasks` なし（2 回目は 6 秒） | 11 | 成功 |
| 再生成 2 回、`--rerun-tasks` あり | 11 | 成功（上の行と同一のファイル） |
| `help` で再生成、続けて `build` で再生成 | 11 | 成功 |

Linux の CI でも `--rerun-tasks` なしの 2 回の再生成で strict モードのビルドが成功した（[run 41160771357](https://github.com/appachan/android-supply-chain-lab/actions/runs/41160771357)）。更新のない `main` では、再生成しても `--refresh-dependencies` を付けても差分は 0 行だった。

条件を分けた最小の再現。Gradle 9.7.1、子の POM を別のリポジトリに置き、本物の署名付き BOM を参照する。keyring は固定した。

| 参照 | BOM | 子のリポジトリの `.asc` | 1 回目 | 2 回目 | 3 回目 |
| --- | --- | --- | --- | --- | --- |
| import | `.module` あり（bc） | なし | 失敗 | 失敗 | 失敗 |
| parent | `.module` あり（bc） | なし | 失敗 | 失敗 | 失敗 |
| import | `.module` あり（bc） | あり | 成功 | 成功 | 成功 |
| parent | `.module` あり（bc） | あり | 成功 | 成功 | 成功 |
| import | POM のみ（log4j-bom） | なし | 失敗 | 成功 | 成功 |
| parent | POM のみ（log4j-bom） | なし | 失敗 | 成功 | 成功 |

- 1 回目の失敗の条件は、親や BOM の POM が子とは別のリポジトリにあり、そのリポジトリに署名があって、子のリポジトリに `.asc` がないことである。`.asc` を置くことだけで失敗が消えた
- import か parent かは関係しない。`.module` の有無も 1 回目の失敗の条件ではない
- POM のみの BOM では親の POM（`logging-parent-7.pom`、`apache-27.pom`）も同じように失敗した
- `.module` がある BOM は、最小の再現では 3 回実行しても揃わなかった。POM のハッシュを手で足すと strict モードのビルドは成功した

### 推測

- writer の登録は最初の 1 件が残るので、空の環境では親を解決した Central の経路が先に登録され、署名が有効なのでハッシュが不要と判断される。strict モードは Google の経路も別に検証するので、署名もハッシュもない状態で失敗する
- 2 回目はキャッシュがあるので親の経路が通らず、子の経路だけが登録され、署名が見つからないのでハッシュが書かれる
- `.module` の有無と実物の結果の違いから、この説明は完全ではない。最小の再現の `.module` ありの BOM では 2 回目に揃わないが、lab の実物は同じ BOM で揃う。BC のライブラリへの依存と buildscript の `classpath` を足しても再現しなかった

### 公式の issue との関係

- [#19228](https://github.com/gradle/gradle/issues/19228)（open）と [#20194](https://github.com/gradle/gradle/issues/20194)（open）は、親や BOM の POM が metadata から欠ける問題である。Gradle の開発者は、解析済みの descriptor がキャッシュにあると親をたどらないことが原因だと[説明している](https://github.com/gradle/gradle/issues/20194#issuecomment-1652095447)。欠ける向きは warm cache で、`--refresh-dependencies` で解消した[報告](https://github.com/gradle/gradle/issues/19228)がある
- lab の現象は別の原因である。空の環境で起き、`--refresh-dependencies` では直らず、`sha256` だけなら起きない。POM を見ていないのではなく、署名が有効と判断された結果ハッシュが書かれない。#20194 には空の `GRADLE_USER_HOME` でも起きるという[報告](https://github.com/gradle/gradle/issues/20194)があり、同じ現象の可能性があるが、再現手順がないので確認していない
- [#24948](https://github.com/gradle/gradle/issues/24948)（open）は、親 POM の `<pgp>` と `trusted-key` が非決定的に変わる報告である。手元の strict モードのビルドの後に増えた 19 行は同じ形だが、関係は確認していない
- 同じ原因の issue は見つけられなかった。[#33500](https://github.com/gradle/gradle/issues/33500) は PR ではなく open の issue で、#19228 の troubleshooting の追加を求めている。現在の[公式ドキュメント](https://docs.gradle.org/current/userguide/dependency_verification.html)にはキャッシュの状態と `--refresh-dependencies` の記述がない

### 一般的な運用例

公開リポジトリでは `--refresh-dependencies` が多い。[Adyen](https://github.com/Adyen/adyen-android/blob/main/.github/workflows/update_verification_metadata.yml)、[Airflow](https://github.com/apache/airflow/blob/main/scripts/ci/prek/regenerate_java_sdk_verification_metadata.py)、[Besu](https://github.com/besu-eth/besu/blob/main/README.md)、[RSKj](https://github.com/rsksmart/rskj/blob/master/scripts/update-verification-metadata.sh)、[keycloak-mock](https://github.com/TNG/keycloak-mock/blob/main/.github/workflows/update-verification-metadata.yml) はいずれも `sha256` だけで、キャッシュがある前提の対策である。[AndroidX](https://github.com/androidx/androidx/blob/androidx-main/development/update-verification-metadata.sh) は `pgp,sha256` で `--clean` を使い #19228 をコメントで参照している。[Renovate](https://github.com/renovatebot/renovate/blob/main/lib/modules/manager/gradle/artifacts.ts) は `--write-verification-metadata <hashTypes> dependencies` を 1 回実行する。[Dependabot で署名も使う例](https://github.com/SimonMarquis/Android-Playground/blob/main/.github/workflows/dependabot-gradle-dependencies.yaml)も 1 回である。`pgp,sha256` を 2 回実行する例は見つけられなかった。`--refresh-dependencies` が効くのは `sha256` の運用で、`pgp` の lab では効かないので、結果は矛盾しない。

### 採用する手順

同じコマンドを空の環境で 2 回実行する。`--rerun-tasks` は結果が変わらないので使わない。`--refresh-dependencies` は空の環境では効果がないので使わない。

2 回で揃う保証はない。最終的な判定は空の環境の `verify` であり、欠けていれば失敗する側に倒れる。`verify` が `.pom` で失敗し、`from repository` が親の配布元と違うときは、配布元の `.asc` で署名を確認してから、その POM の sha256 を metadata に手で足す。

## 検証の対象

公式の説明は Gradle 9.7.1 のドキュメントによる。

[Verification Metadata](https://docs.gradle.org/9.7.1/userguide/dependency_verification.html#sub:verification-metadata):

> Gradle verifies any artifact downloaded via its dependency management engine, including but not limited to:
> - Artifact files (e.g., JAR files, ZIPs) used during the build
> - Metadata artifacts (POM files, Ivy descriptors, and Gradle Module Metadata)
> - Plugins (both project and settings plugins)
> - Artifacts resolved via advanced dependency resolution APIs
>
> Gradle does not verify changing dependencies (specifically SNAPSHOT versions) or locally produced artifacts (such as JARs generated during the build itself).

[Scope](https://docs.gradle.org/9.7.1/userguide/dependency_verification.html#sec:verification-scope):

> Specifically, the same file applies to all subprojects, the root project, and buildSrc.

[`verify-metadata`](https://docs.gradle.org/9.7.1/userguide/dependency_verification.html#sec:disabling-metadata-verification):

> By default, Gradle verifies both artifacts (JARs, ZIPs, etc.) and their metadata files (POM files, Ivy descriptors, Gradle Module Metadata).
>
> Disabling metadata verification reduces security. Compromised metadata files could introduce malicious transitive dependencies into your build.

[`trusted-artifacts`](https://docs.gradle.org/9.7.1/userguide/dependency_verification.html#sec:skipping-javadocs):

> By default, Gradle verifies all downloaded artifacts, including javadocs and sources.
> This can cause issues with IDEs that automatically download them during import.

ドキュメントには buildscript、`files()`、ファイルリポジトリの記述がない。ここは [`ExternalModuleComponentResolverFactory`](https://github.com/gradle/gradle/blob/v9.7.1/platforms/software/dependency-management/src/main/java/org/gradle/api/internal/artifacts/ivyservice/ivyresolve/ExternalModuleComponentResolverFactory.java) と実験を根拠にする。このクラスはリポジトリごとに検証のラッパーを被せていて、local と remote の両方の経路が通り、buildscript と project の区別がない。SNAPSHOT は [`DependencyVerifyingModuleComponentRepository`](https://github.com/gradle/gradle/blob/v9.7.1/platforms/software/dependency-management/src/main/java/org/gradle/api/internal/artifacts/ivyservice/ivyresolve/DependencyVerifyingModuleComponentRepository.java) が changing module を飛ばしている。

未知の依存を含む最小のビルドを、空の metadata で実行した結果は次のとおり。

| 対象 | 根拠 | 結果 |
| --- | --- | --- |
| リリース版（ファイルリポジトリ） | ソース | 失敗（検証される） |
| project の plugin | 公式 | 失敗（`detachedConfiguration1`） |
| settings の plugin | 公式 | 失敗（`detachedConfiguration1`） |
| buildscript の `classpath` | ソース | 失敗（`configuration 'classpath'`） |
| SNAPSHOT（ファイルリポジトリ） | 公式、ソース | 成功（検証されない） |
| `files()` の jar | ソース | 成功（検証されない） |

依存管理の外で取得するものは対象外である。Gradle の配布物は ADR-0001 の `distributionSha256Sum` が扱う。POM と `.module` は PR #1 の失敗、jar と aar は論点 5 で確認した。

## 鍵サーバー

`<key-servers enabled="false">` を採用する。[公式](https://docs.gradle.org/9.7.1/userguide/dependency_verification.html#sec:local-keyring-only)は次のとおりで、どちらも実際に確認した。

> Only the local keyring file will be used, and if a key is missing, the build will fail.
>
> If you are asking Gradle to generate verification metadata and an existing file sets enabled to false, this flag will be ignored so that potentially missing keys can be downloaded.

設定は次のようにする。

```xml
<key-servers enabled="false">
   <key-server uri="https://keyserver.ubuntu.com"/>
   <key-server uri="https://keys.openpgp.org"/>
</key-servers>
```

| 確認 | 結果 |
| --- | --- |
| 現在の keyring で空の環境の strict モードのビルド | 成功。[実装](https://github.com/gradle/gradle/blob/v9.7.1/platforms/software/dependency-management/src/main/java/org/gradle/api/internal/artifacts/verification/signatures/DefaultSignatureVerificationServiceFactory.java)は `EmptyPublicKeyService` を使い、外部に問い合わせない |
| keyring に鍵がない依存の strict モードのビルド | 失敗。`Key servers are disabled, this can indicate that you need to update the local keyring` |
| 再生成 | `Will use key servers to download missing keys` を出して鍵を取得する。on と off の取得の成功率に差はなかった（3 回中 1 回と 2 回） |
| 設定の保持 | `enabled="false"` と子要素の `key-server` は再生成で残る。検査のスクリプトの設定の比較も通る |
| Dependabot の PR | [PR #4](https://github.com/appachan/android-supply-chain-lab/pull/4) で下記のとおり成功 |

鍵の取得の失敗は設定ではなく既定のサーバーの一覧の問題である。[既定](https://github.com/gradle/gradle/blob/v9.7.1/platforms/software/dependency-management/src/main/java/org/gradle/api/internal/artifacts/ivyservice/ivyresolve/verification/DefaultKeyServers.java)の 4 台には解決できない `ha.pool.sks-keyservers.net` が含まれ、[順序はランダムで、リトライの上限は 5 秒](https://github.com/gradle/gradle/blob/v9.7.1/platforms/software/security/src/main/java/org/gradle/security/internal/PublicKeyDownloadService.java)である。公開鍵は curl なら毎回 1 秒未満で取得できた。lab の構成で新しい鍵が必要な再生成を比較した結果は次のとおり。

| key-server | 鍵の取得に成功 |
| --- | --- |
| 既定の 4 台 | 11 回中 7 回 |
| 2 台に限定 | 5 回中 5 回 |

因果は機構からの推測で、試行数は少ない。ただし追加の費用はないので 2 台に絞る。

新しい鍵が必要な更新の確認。一時的に `snakeyaml:1.33` を `app/build.gradle.kts` に足した。2.x は署名鍵が違い、Dependabot のグループ更新が新しい鍵を要求する。

| 設定 | 結果 | 実行 |
| --- | --- | --- |
| 既定の 4 台 | 鍵の取得に失敗。`ignored-key` とハッシュに落ち、`Ignored keys` に出た。`verify` は成功 | [run 41165764108](https://github.com/appachan/android-supply-chain-lab/actions/runs/41165764108)、[run 41165999242](https://github.com/appachan/android-supply-chain-lab/actions/runs/41165999242) |
| 2 台 | 鍵を取得。keyring が 15 行増え、`trusted-key` が `org.yaml:snakeyaml:2.7` に限定で追加された。`verify` は成功 | [run 41169104329](https://github.com/appachan/android-supply-chain-lab/actions/runs/41169104329)、[run 41169362370](https://github.com/appachan/android-supply-chain-lab/actions/runs/41169362370) |

コミットは [e16a89a](https://github.com/appachan/android-supply-chain-lab/commit/e16a89af3c202b83308d55c7442ea9eb89c5ab33) で、`verified: true` である。本文の `unknown owner` は、この鍵の keyring に UID がないことを示す。確認後、一時依存は `main` から外した。

off の効果は信頼の範囲ではなく、`verify` の決定性にある。信頼の根拠は metadata の fingerprint で、鍵サーバーから取得した鍵が自動で信頼されることはない。ただし再生成は例外で、取得した鍵を信頼に追加するので、人の確認が必要な点は変わらない。

既知の揺らぎとして、鍵が取得できたのに keyring に入らない場合があった。最小の構成で `Exported 0 keys` が 1 回目で 10 回中 5 回、2 回の再生成の後で 10 回中 2 回起きた。既定の 4 台の構成で、原因は確認していない。`trusted-key` は書かれるので、on では `verify` が鍵サーバーから取得して隠れる。off なら `verify` が失敗して気付ける。

## 記事との比較

[Best Practices for Gradle Dependency Verification](https://britter.dev/blog/2026/06/01/gradle-dependency-verification-best-practices/)（2026-06-01）と [Enabling Gradle Dependency Verification](https://britter.dev/blog/2025/02/10/gradle-dependency-verification/)（2025-02-10）を比較した。方針は Dependabot の環境向けに決める。記事は Renovate が前提で、Renovate は[再生成を `dependencies` で 1 回実行する](https://github.com/renovatebot/renovate/blob/main/lib/modules/manager/gradle/artifacts.ts)。Dependabot は metadata を更新しないので、この ADR の再生成のワークフローが必要になる。

| 推奨 | 判定 | 理由 |
| --- | --- | --- |
| checksum より PGP の鍵を信頼する | 採用 | 論点 1 |
| armored の keyring | 採用 | 論点 1 |
| 鍵サーバーを無効にする | 採用（上記） | keyring の欠けを検出できる。記事の「安全性への影響なし」は `verify` については同意する。再生成では無視されるので、記事の「鍵の判断を人が持てる」はこの設定だけでは実現しない |
| sources と javadoc を信頼する | 採用 | 論点 2 |
| 鍵の取得の失敗を手で keyring に足す | 手順として採用 | `ignored-key` になったときの選択肢 |
| 署名のない成果物の値を手で確認する | 部分的に採用 | 確認の対象としてコミット本文に出す。`origin` の書き換えは運用しない |
| metadata を変更するのは人の確認のため（ロボットの仕事ではない） | 採用 | コミットはワークフローが作るが、承認は人が行う。記事の「変更は稀であるべき」は Dependabot の更新のたびに差分が出るので、検査と分類で補う |
| `verify-metadata` を `false` にする | 不採用 | 公式が `reduces security` としている。POM は依存の版を変えられるので、グループ単位で鍵を信頼すると、署名された古い版へ差し替えられても検知できない可能性がある（推測、未検証）。実測の削減は 314 行から 286 行で約 9% だけだった。この設定なら再生成は 1 回で strict モードのビルドが通り、2 回の再生成の問題は消えるが、検証を減らす理由にはしない |
| 鍵の `version` を消して全ての版を信頼する | 不採用 | 記事自身が最も危険な判断としている。metadata の信頼 79 件のうち 23 件は版を限定している。Gradle が生成した範囲のまま残し、次の版で再度確認する |
| 手で component を `trusted-key` に移す、ハッシュを消す | 不採用 | 手の編集はワークフローの再生成と競合し、差分が読みにくくなる |
| metadata にコメントで注釈する | 不採用 | 再生成でコメントは消える（手元で確認）。判断の記録はコミット本文と ADR に残す |
| `gradle-*-src.zip` を `trusted-artifacts` に入れる | 保留 | IntelliJ の sync の対策である。Android Studio で確認していないので、失敗してから足す |
| `failOnNonReproducibleResolution()` か依存のロック | 対象外 | ADR-0003 の論点 8 で比較した。記事の BouncyCastle の版の範囲の例は、metadata が更新と無関係に壊れる原因になる |
| `org.gradlex.jvm-dependency-conflict-resolution` | 不採用 | lab の依存は少なく、検証の対象の plugin が増える。rss-reader で依存の重複が問題になれば見直す |

## cooldown と Google Maven のライブラリ

[Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference) によれば、version update には `cooldown` を設定しなくても既定で 3 日の cooldown が適用される（`Apply a default cooldown period of 3 days to version updates, even when cooldown is not configured.`）。security update は対象外である（`This default cooldown does not apply to security updates.`、`The cooldown option is only available for version updates, not security updates.`）。`exclude` は `*` のワイルドカードに対応し、`include` より優先される。

Google Maven のライブラリでは、公開日が `maven-metadata.xml` の最新の 1 バージョン分しか取れていない。ログの `Release date not available for version 1.13.0 - filtering out` のとおり、公開日の分からないバージョンは除外される。最新が pre-release の `androidx.activity:activity-compose`（1.14.0-alpha03）と `androidx.test:runner`（1.8.0-alpha03）は、安定版がすべて除外されて更新されない。BOM は最新が安定版なので更新される（[PR #8](https://github.com/appachan/android-supply-chain-lab/pull/8)）。

catalog の `activity-compose` を 1.12.4、`androidx.test:runner` を 1.6.2、`software.amazon.awssdk:annotations` を 2.56.0 に下げて、設定ごとに実際のジョブを実行した。

| `cooldown` の設定 | `activity-compose`、`androidx.test:runner` | `software.amazon.awssdk:annotations` | PR |
| --- | --- | --- | --- |
| `default-days: 7`、`exclude: androidx.*` | 除外 0 件で 1.13.0、1.7.0 に更新される | 5 バージョンを除外して 2.57.3（`cooldown days: 7`） | [PR #11](https://github.com/appachan/android-supply-chain-lab/pull/11) |
| 設定なし | 26 バージョンが `Release date not available` で除外され、更新されない | 3 バージョンを除外して 2.57.5（`cooldown days: 3`） | [PR #12](https://github.com/appachan/android-supply-chain-lab/pull/12) |

設定なしの結果のとおり、この問題は cooldown を外しても解決しない。既定の 3 日が同じ経路を通る。ジョブの定義には `cooldown` がないが、ログには `cooldown days: 3` が出る。

対処として `androidx.*` を `exclude` に入れた。ジョブの定義に `"exclude":["androidx.*"]` として渡り、Maven Central の依存の cooldown は残る。代償として、androidx のバージョンは公開直後でも提案される。`androidx.*` に当たらない Google Maven のライブラリには、同じ問題が残る。

### 古い PR の扱い

[PR #1](https://github.com/appachan/android-supply-chain-lab/pull/1) は `[dependabot skip]` のない再生成のコミットがあるので、`@dependabot rebase` は `edited by someone other than Dependabot` で断られた。`@dependabot recreate` では、`Looks like com.android.application is updatable in another way, so this is no longer needed.` として Dependabot が close した。グループの更新があるので、個別の PR は作り直されない。

`[dependabot skip]` のある再生成のコミットを持つ [PR #13](https://github.com/appachan/android-supply-chain-lab/pull/13) では、`@dependabot rebase` の 1 回目は `Looks like this PR is already up-to-date with main!` と返された。main を進めた後の 2 回目は 20 分以上反応がなく、Dependabot のジョブも起動しなかった。再生成のコミットが rebase でどう扱われるかは分かっていない。

### ruleset の下での判定

main に rss-reader の `default` と同じ ruleset（id 26267113）を設定した。`deletion`、`non_fast_forward`、`required_signatures`、`pull_request`、`required_status_checks` で、`bypass_actors` はない。

PR #13 の head の 2ce8f59 は再生成のコミットで、その後に手動で起動した CI（[run 41190375435](https://github.com/appachan/android-supply-chain-lab/actions/runs/41190375435)）の `verify` が成功している。この状態の判定は次のとおりである。

| 確認 | 結果 |
| --- | --- |
| `mergeStateStatus`、`mergeable` | `BLOCKED`、`MERGEABLE` |
| REST の `mergeable_state` | `blocked` |
| `verify` の check run | `SUCCESS`、`isRequired: true`、app 15368、`pull_requests` に PR あり |
| `statusCheckRollup`、`gh pr checks --required` | 空、`no checks reported` |
| 同じ commit の `pull_request` の check suite | `CI` と `Regenerate verification metadata` が `ACTION_REQUIRED` |
| 署名 | 73718f0、2ce8f59 とも `verified: true`、`reason: valid` |
| `reviewDecision` | null（レビューの要求なし） |

リポジトリの管理者が Approve workflows to run を押すと、`pull_request` の `CI`（[run 41190379016](https://github.com/appachan/android-supply-chain-lab/actions/runs/41190379016)）と `Regenerate verification metadata`（[run 41190379158](https://github.com/appachan/android-supply-chain-lab/actions/runs/41190379158)）が attempt 2 として実行されて成功した。

| 確認 | Approve の前 | Approve の後 |
| --- | --- | --- |
| `mergeStateStatus` | `BLOCKED` | `CLEAN` |
| `statusCheckRollup` | 空 | `SUCCESS`（`verify` は `isRequired: true`） |
| `verify` の実行の event | `workflow_dispatch` | `pull_request` |

手動で起動した `verify` では必須チェックを満たせないと確定した。check run は `isRequired: true` と表示されるが、PR の判定には数えられない。必要なのは `pull_request` の実行である。

変わったのはチェックだけなので、`required_signatures`、`require_extra_approval_for_unattributed_changes`、承認数 0 の `pull_request` の規則は、再生成のコミットがあっても判定を止めない。PR #13 は merge していないので、実際の merge の成否は `CLEAN` の判定までの確認である。

Approve で再実行された `Regenerate verification metadata` は差分を作らず、head は 2ce8f59 のままだった。再生成のやり直しで再度の Approve が必要になる状況は起きていない。

### Approve workflows to run が必要になる条件

条件は、`GITHUB_TOKEN` による push が作る `pull_request` の実行である。[GITHUB_TOKEN の説明](https://docs.github.com/en/actions/concepts/security/github_token)に、`events triggered by the GITHUB_TOKEN will not create a new workflow run` の例外として、`the resulting pull_request event creates workflow runs in an approval-required state` とある。同じページに、`workflow_dispatch` は常に実行を作ること、GitHub App の installation access token か personal access token を使えばこの承認を避けられることが書かれている。

直近 100 件の実行の記録は次のとおりである。

| 場合 | event | actor | 結果 |
| --- | --- | --- | --- |
| Dependabot のコミット | `pull_request` | `dependabot[bot]` | 20 件すべて承認なしで実行された |
| 再生成のコミット | `pull_request` | `github-actions[bot]` | 14 件すべて承認待ちになった（attempt 1）。PR が閉じた後に `failure` へ変わるものがある |
| `Run CI on the new commit` | `workflow_dispatch` | `github-actions[bot]` | 承認なしで実行されるが、必須チェックを満たさない |

fork の設定は関係しない。PR の head は同じリポジトリで、`actions/permissions/fork-pr-contributor-approval` の `first_time_contributors` は [fork の PR](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks) の承認の設定である。environment もない。

- 再生成のコミットがある PR: 毎回 Approve が必要である。再生成のコミットが増えるたびに必要になる
- 再生成のコミットがない PR: 不要である。[PR #11](https://github.com/appachan/android-supply-chain-lab/pull/11) と [PR #12](https://github.com/appachan/android-supply-chain-lab/pull/12) は Dependabot のコミットだけで、`pull_request` の `verify` が承認なしで動いた。metadata に更新先の成果物が既にあるか、成果物が group の鍵で検証できる場合である

rss-reader の設定を読み取りで確認した。public で、`fork-pr-contributor-approval`、`default_workflow_permissions`、`can_approve_pull_request_reviews` は lab と同じで、environment もない。同じ方式を適用すれば同じ Approve が必要になる。

### 手動の verify の扱い

`Commit verification metadata` の `Run CI on the new commit` は残す。必須チェックは満たさないが、Approve の前に検証の結果を確かめられる。

### lockfile を含む PR

ADR-0003 の方式を main に merge した後の PR で、再生成のコミットの `verified` は [PR #6](https://github.com/appachan/android-supply-chain-lab/pull/6)、[PR #7](https://github.com/appachan/android-supply-chain-lab/pull/7)、[PR #8](https://github.com/appachan/android-supply-chain-lab/pull/8)、[PR #9](https://github.com/appachan/android-supply-chain-lab/pull/9) のすべてで `true` だった。[PR #7](https://github.com/appachan/android-supply-chain-lab/pull/7) は 3 つの lockfile を含む。結果の一覧は ADR-0003 の論点 9 にある。

## 運用手順

Dependabot の PR の確認:

1. `Commit verification metadata` のコミットの本文を読む。commit がなければ、依存の成果物の変更がなく、CI はそのまま判断できる
2. 新しい鍵の fingerprint と範囲を配布元の公式情報で確認する
3. ハッシュで受け入れる成果物を確認する。特に signature の警告が付いた行を確認する
4. Kotlin の互換性の表で版の範囲を確認する
5. wrapper の更新があれば、`gradlew` と `gradlew.bat` の diff を確認する
6. `Rejected` で `Commit` が失敗したときは merge しない。原因を調べるまで再生成しない
7. `verify` が `.pom` で失敗したら、「2 回の再生成が必要な原因」の手順で確認する
8. 再生成のコミットがある PR では、Approve workflows to run を押して `pull_request` の `verify` を実行する。手動で起動した `verify` は必須チェックを満たさない
9. `verify` の成功と `mergeStateStatus` の `CLEAN` を確認して merge する

`Regenerate` が失敗したときは、更新そのものがビルドできないので人が判断する。

`Commit verification metadata` が `Branch not found` で失敗したときは、Dependabot が PR を置き換えてブランチを消した後の実行なので、対応は要らない。

手元で metadata を変更するとき（依存を手で追加したときなど）:

```sh
GRADLE_USER_HOME="$(mktemp -d)" sh -c '
  ./gradlew --write-verification-metadata pgp,sha256 --export-keys --write-locks build
  ./gradlew --write-verification-metadata pgp,sha256 --export-keys --write-locks build
'
```

`ignored-key` が出たら、鍵の取得の一時的な失敗か確認する。残すと該当の成果物はハッシュで検証される。鍵を入れるなら再生成をやり直すか、手元で再生成する。`verify` が `Key servers are disabled` で失敗したら、keyring に鍵が入っていないので同じように直す。

使わなくなった版の行は Gradle が消さない。ときどき `components` を空にして生成し直す。これは差分が大きいので、Dependabot の PR とは分ける。

検証の失敗を調べるときは、`build/reports/dependency-verification/` の HTML を読むか、`org.gradle.dependency.verification.console=verbose` を付ける。`--dependency-verification lenient` は検証を無効にするので、CI では使わない。

## rss-reader に適用するときの差分

rss-reader は読むだけで、まだ適用していない。

- `dependabot.yml` がないので追加する。`cooldown` の `exclude` に `androidx.*` を入れる
- 再生成のコミットがある Dependabot の PR は、ruleset の必須チェックのために Approve workflows to run が毎回必要になる（「Approve workflows to run が必要になる条件」）
- `ci.yml` に `workflow_dispatch` を追加する。`verify` のジョブ名はそのままでよい
- `concurrency` は `github.ref` で分かれている。dispatch と PR の run は ref が違うので互いに取り消さない想定だが、確認していない
- `key-servers` の設定は lab と同じものを使う。`build-logic` と foojay の依存があるので、最初の生成で `ignored-key` がなくなるまで確認する
- `setup-gradle` を使っている。ADR-0001 の理由で、再生成のジョブには入れない。キャッシュから入った依存も検証されることは手元で確認したが、`setup-gradle` との組み合わせは確認していない
- 再生成のタスクを CI と揃える。`spotlessCheck`、`detekt`、`lint`、`test` は実行時に依存を解決するので、`build` に含まれない分があれば明示する
- `build-logic` は included build で、ルートの metadata を使う。lab に同じ構成を足して確認した（ADR-0003 の論点 7）。`settings.gradle.kts` の foojay の plugin も検証の対象になる
- `build` で再生成した metadata で `assembleDebugAndroidTest` も空の環境の strict モードのビルドを通る。androidTest の分は lint のタスクが取得する。再生成から `lint` や `test` を外さない
- 再生成のコマンドに `--write-locks` を入れ、`gradle.lockfile` もコミットの対象にする（ADR-0003）
- `distributionUrl` は 9.1.0、AGP は 9.0.1 で lab と異なるので、metadata は rss-reader で生成する。鍵の取得の失敗があれば、論点 2 の方法で ignored key をなくす
- ruleset は `main` だけに適用され、署名付きコミット、`verify`、merge コミットを要求する。再生成コミットは `verified: true` なので署名の条件を満たす見込みである
- ruleset の `require_extra_approval_for_unattributed_changes` が bot のコミットにどう作用するかは確認していない
- Robolectric など、Gradle の外で取得するものはこの検証の対象外の可能性がある。適用のときに確認する
- 版の互換性の判断は rss-reader の組み合わせで行う

## Consequences

- 依存の更新で、人が見る差分が新しい鍵と無署名の成果物に絞られる
- Dependabot の PR ごとに `Regenerate` が再生成を 2 回実行する。2 回目はタスクが最新なので短い
- CI の `verify` の成功は metadata の一貫性だけを示す。承認の根拠にしない
- 再生成のコミットがある PR は、人が Approve workflows to run を押すまで merge できない
- 新しい成果物の初回の信頼は、人の確認に依存する。配布元が侵害されていれば再生成も同じものを記録する
- グループ単位の鍵の信頼は、鍵が盗まれると新しい成果物も通す
- Google Maven のプラグインには cooldown が効かない
- `androidx.*` は cooldown の対象外なので、公開直後のバージョンも提案される
- `androidx.*` に当たらない Google Maven のライブラリは、最新が pre-release だと Dependabot が更新しない
- `verify` は鍵サーバーに依存しない。keyring の欠けは `verify` の失敗になる

## 未解決

- Dependabot の公開日の取得が Google Maven で最新の 1 バージョンに限られる原因は、ログからの判断で、実装では確認していない
- `Exported 0 keys` の原因は確認していない
- `[dependabot skip]` のあるコミットでの `@dependabot rebase` の結果は確認できていない。main を進めた後のコメントに Dependabot が反応しなかった
- ruleset の下で再生成のコミットを実際に merge してはいない。`mergeStateStatus` の `CLEAN` までの確認である
- `pull_request` の承認待ちの実行を REST API で承認できるかは確認していない。GitHub App の token に変えて承認を避けるかは判断していない
- Kotlin の互換性の範囲を超える提案を `ignore` で止めるかは、rss-reader の適用のときに決める
- `.module` のある BOM が lab の実物では 2 回で揃い、最小の再現では揃わない理由は確認していない
